# Domain glossary

pulsarix is a product-feedback and issue-tracking tool: organisations, members, projects,
issues, comments, activity, notifications, attachments, search, realtime subscriptions and
client intake (widget keys and a public intake endpoint). The code, the GraphQL schema and
the collections speak English, the default language of the product (French is offered). Terms
join this table slice by slice.

## Public states, links, impact and type (A15)

- **`Status.publicState`** (`received`, `inProgress`, `resolved`, `declined`) is what a reporter sees of a status, never its name. It defaults by category (triage, backlog, todo: received; inProgress: inProgress; done: resolved; cancelled: declined), is set through `createStatus` / `updateStatus` (a category change moves a status that still wears the old category's default), and is read as the category's default on a status stored before the field (no migration).
- **A report's `publicState`** is derived, in order: declined (the report was declined, or its issue's status maps to declined; no reason then), resolved (the reporter resolved it and has not reopened since), in progress (reopened, until the issue's mapped state differs from `reopenedFrom`), else the issue's mapped state, `received` with no issue. `resolvedByReporterAt`, `reopenedAt` and `reopenedFrom` are written by the later reporter slices. The tracking read gives `publicState` and the public `declineReason`, never a status name. On `/public/graphql` `publicState` is the `PublicState` enum (same four values as the wire strings it replaced). A type's label (`Bug`, `Question`, `Suggestion`) is matched case-insensitively, as the `labels` unique index (`projectId`, `name`, collation `en` strength 2) is, so a team's own `bug` is reused and `BUG` is refused as a second label.
- **Decline reasons**: shown to the reporter when `declineReasonPublic` is true (every decline since widget v3). Reports declined earlier lack the flag and keep their reason hidden.
- **`linkClientReport(id, issueId)`** accepts a new report into an existing issue of the same project (`linkedAt`, files released, closed at once when the issue is done or cancelled). Several reports may share one `issueId`; the issue's closing and reopening follow every one (`followIssue`).
- **Impact and type** come from the submit input. `impact` prefills the priority at acceptance (`blocking` High, `annoying` Medium, `minor` Low; urgent stays the team's) with `Issue.priorityOrigin` `client`, which becomes `team` once a member changes the priority (also the value for every issue a member makes or stored before it; `auto` is reserved). `type` (`bug`, `question`, `suggestion`) adds the label Bug, Question or Suggestion, made in the project on first use and matched without regard to case.

## Mail links

The UI pages the mails link to, fixed here (the UI never renames them alone). Each posts its token
back from a button: a mail scanner follows a link, so a GET never spends it.

| Path                          | Mail           | Mutation                   |
| ----------------------------- | -------------- | -------------------------- |
| `/invitations/accept?token=`  | invitation     | `acceptInvitation`         |
| `/auth/magic-link?token=`     | sign-in link   | `confirmMagicLink`         |
| `/auth/reset-password?token=` | password reset | `resetPassword`            |
| `/auth/verify-email?token=`   | e-mail proof   | `confirmEmailVerification` |

The sign-in link is behind `PULSARIX_MAGIC_LINK` (off by default; `.env.example`, `deploy/.env.example`). Off, `requestMagicLink` answers true and sends nothing, `confirmMagicLink` is refused 503 `auth.errors.unavailable`, and `authConfig { magicLink }` is false so the sign-in screen hides the option.

**E-mail verification.** `signUp` does not prove the e-mail (`Viewer.emailVerified` is false). The signed-in account calls `requestEmailVerification`, which answers true whether or not the e-mail is proved already (then nothing is sent): the mail runs in the background, and the 429 comes from the account's Redis limit (10 an hour, `accounts.email-verification-account`, 503 if Redis cannot be asked) and janus's per-address throttle (5 per 10 minutes). `/auth/verify-email` posts its token to `confirmEmailVerification`, which needs a session and is bound to it: a token issued to another account is `auth.errors.invalid-token` and stays usable by its owner. The link proves the address only; the password and the second factor are kept (a first proof through a sign-in link or an invitation still drops them). It adds no error code: a lapsed, spent, unknown or foreign token is `auth.errors.invalid-token`.

## File routes

Files do not go through GraphQL. The routes sit beside `/graphql` and need the same headers
(`x-pulsarix-client`, `Authorization: Bearer`, `x-organization-id`); without `S3_BUCKET`,
`S3_ACCESS_KEY` and `S3_SECRET_KEY` they answer 503 `attachments.errors.unavailable`.

## Public endpoint

`POST /public/graphql` is the product's only unauthenticated surface, apart from `/graphql`'s own
sign-in mutations. It has a schema of its own (three fields) and runs three **persisted operations**,
named by `id` (`{ "id": "widgetConfig", "variables": {...} }`); a document, an introspection query or
any other key is 400 `intake.errors.persisted-only`. The body is JSON only (415 otherwise) and at most
64 KiB.

- **CORS** answers only an origin some live key allows (the preflight), and every call checks the key's
  own list; a foreign or missing `Origin` is 403 `intake.errors.origin-not-allowed` with no CORS header.
  A browser sends `Origin`; a script can forge it, so it is a guard against other sites, and the limits
  are the guard against scripts.
- **Rate limits** (`@softistx/redis`, `src/modules/intake/intake.limits.ts`): per address 120 reads or
  submits per 10 minutes; per key 60 per hour; per address and key 5 per 10 minutes; per e-mail 3 per
  hour; per organisation 300 per hour; tracking reads 30 per 10 minutes per address. A decoy upload slot takes one use per 15 minutes (`intakeDecoySlot`); a replay answers 409 `intake.errors.ticket-used`, not 429. Over a limit: 429
  `intake.errors.too-many-requests` with `Retry-After`. Without Redis (or if it fails) the endpoint
  answers 503 `intake.errors.unavailable`: it never runs unmetered. The address is `TRUSTED_PROXIES`'
  reading of `X-Forwarded-For`; unset, it is the connection's; an IPv6 address counts by its /64. The UI server's tracking reads share one bucket per client only if it appends the client's address to `X-Forwarded-For` from inside `TRUSTED_PROXIES`.
- **Anti-abuse** (Q10): the honeypot field `website` (told it worked, nothing kept), a minimum fill time
  (`filledInMs`, 400 `intake.errors.too-fast`), the length limits, control characters stripped, and the
  tracking mail repeats nothing the sender typed.
- Every answer carries `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex`.

## Public upload by ticket (A12)

- `submitClientReport` takes `files: [{role: screenshot|file, name, type, size}]` (at most 4: 1 screenshot, 3 files; PNG, JPEG, WebP, PDF, a screenshot never a PDF; 5 MB each, 12 MB in all) and answers `files: [{slot, role, ticket, expiresAt}]`. `widgetConfig.attachments` says whether the key takes files (`attachmentsEnabled` on the key, default true).
- Each file is then sent with `PUT /public/media/report-files/<slot>`: the raw file as the body, `Content-Type` and `Content-Length` equal to the declared ones, the ticket in `x-pulsarix-ticket`, the key's `Origin`. A ticket is `<payload>.<HMAC-SHA256>` signed with `INTAKE_TICKET_SECRET` (at least 32 characters; unset, derived from `API_PROXY_SECRET`), valid 15 minutes, one upload per slot. Success is `200 {slot, state: "received"}` and the file is `quarantined`; a failed upload frees the slot until its deadline.
- The team reads a report file with `GET /media/report-files/<key>/<size>` (`full`, `file` for a PDF, or `256`), through the UI server (`x-pulsarix-client`, a session, `attachment:read`). The URLs come from `ClientReport.files` (needs `issue:write`, the inbox) and `Query.issueClientReportFiles(issueId)` (needs `attachment:read`, released files only). A `quarantined` file needs `issue:write` besides; otherwise it answers the same 404 as a missing one. Responses are `private, no-store`, a PDF as an attachment. Accepting a report releases its files in place (the bucket objects do not move); declining keeps them quarantined.
- Every refusal comes before a byte of the body is read. Byte limits (KiB per ticket size): 36 MiB per 10 minutes per address and key, 240 MiB per hour per key; 429 with `retry-after`.
- A honeypot report gets decoy tickets: their PUT answers 200 and stores nothing; a replay answers 409 `ticket-used`, like a real ticket. A report sent too fast stays a 400 with no tickets.
- The team hears of a stored file on the `clientReportFileReceived(projectId)` subscription.
