# Domain glossary

pulsarix is a product-feedback and issue-tracking tool: organisations, members, projects,
issues, comments, activity, notifications, attachments, search, realtime subscriptions and
client intake (widget keys and a public intake endpoint). The code, the GraphQL schema and
the collections speak English, the default language of the product (French is offered). Terms
join this table slice by slice.

| Code             | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Module`         | A unit of the API declared by one `defineModule` manifest and listed in `src/modules/registry.ts`: its schema, resolvers, collections, permissions, codes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `Registry`       | The ONE list of modules (`src/modules/registry.ts`). Adding a module is one line there.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `Kernel`         | `src/core/`: what every module may use. It depends on no business module. It holds `system`, `access`, `accounts`, `organisations`, `members` and `invitations`. Business modules live in `src/modules/`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `Organisation`   | The tenant: a team or company. Registered in the core database (`organisations`), with its own database `pulsarix_org_<id>` (plan Q2). Named in a request by `x-organization-id`, its id or its slug (the header and the `tenancy.errors.*` codes keep @alxia/tenancy's American spelling).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `Account`        | A janus user, global, signed in by e-mail. It belongs to any number of organisations. Not a record of an organisation's database.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `Member`         | An account holding a role in an organisation (janus relation `organization:<id>#<role>@user:<id>`). One role per organisation; two roles are a `conflict` that grants no access.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `Role`           | `owner`, `admin`, `member`, `viewer`, in code (plan Q13). The permissions of a role come from the module manifests (`permissions`, `defaultGrants`); the owner holds every one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `Permission`     | `<area>:<action>` (`member:manage`). `organisation:create` is not a role's: every signed-in account holds it (`Viewer.permissions`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `Invitation`     | An organisation's invitation of an e-mail address with a role. Its link is valid 7 days; only the token's sha256 is stored. Accepting proves the e-mail and makes or finds the account.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `Second factor`  | A TOTP code from an authenticator app, optional per account. Once active, a sign-in answers `SECOND_FACTOR_REQUIRED` with a challenge instead of a session. Ten recovery codes replace a lost app.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `Step-up`        | A fresh proof of identity (a mailed code, or the app's code) that a role change, a removal or disabling the second factor ask for when the session's last proof is older than 10 minutes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `Project`        | A place where issues are tracked, in the organisation's database. Its `key` (`ABC`: 2 to 10 capitals or digits) is unique in the organisation and never changes; archiving hides it, deleting does not exist.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `Status`         | A step of a project's workflow, with a category (`triage`, `backlog`, `todo`, `inProgress`, `done`, `cancelled`), a colour and a gap-free `order`. A new project gets six, one per category. A status issues stand on cannot be deleted (409).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `Label`          | A coloured tag of a project; its name is unique in the project.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `Issue`          | A piece of work in a project, in the organisation's database. Its `key` (`ABC-12`) is the project's key and its `number`, which counts from 1 per project with no gap (a deleted issue's number is not given again). It has a status, a priority, an assignee, labels, a parent, dates and watchers.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `Comment`        | A note on an issue, with a rich-text body, its author and a `public` flag (a reply the tracking page shows). Its `@[Label](id)` mention markers are parsed by the server, each id is checked against the organisation's members (a stranger is refused), and the members found are stored as `mentionIds`. Only the author or an admin edits or deletes it, and only the author sets or changes `public` (an admin cannot flip another's visibility); deleting an issue deletes its comments.                                                                                                                                                                                                                                                                                       |
| `Rank`           | The place of an issue among those of its status: a string that sorts by plain order, so a move writes only the moved issue. `moveIssue` names the issues that end up above (`beforeId`) and below (`afterId`) it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `Activity`       | One row of the append-only journal of a project's issues (`created`, `updated`, `moved`, `deleted`, `commented`, `commentEdited`, `commentDeleted`), with the fields it changed (`changes`: field, from, to, as text). It is written in the transaction of the change it records and never updated or deleted, so a deleted issue keeps its history. Read with `activity(projectId \| issueId)`, newest first.                                                                                                                                                                                                                                                                                                                                                                      |
| `Live event`     | What a subscription (`projectBoard`, `issueChanged`, `notificationReceived`, `clientReportReceived`) delivers, over server-sent events. Published to Redis pub/sub (`REDIS_URL`; in this process alone without it) only after the transaction commits, from the activity row. Fire-and-forget: a client that missed one refetches. A stream checks the viewer's right every 30 s and ends after 15 min idle or an hour.                                                                                                                                                                                                                                                                                                                                                             |
| `Notification`   | A member's message that something concerns them, in the organisation's database, made inside the transaction of the change that caused it. Kinds: `mention` (named in a comment), `assigned` (a new assignee of an issue), `watchedChange` (an issue they watch was changed, moved or commented). The actor is never notified; one event gives at most one notification per recipient, the strongest kind winning; a comment's mention is told once, whatever the edits. Read with `notifications(unread)` and `unreadNotificationCount`, marked with `markNotificationsRead`. Each new one is published as a live event (`notificationReceived`) with the unread count.                                                                                                            |
| `Digest`         | The e-mail of what a member has neither read nor been mailed yet, sent 15 minutes after a notification by a job of the `notification-digest` Redis queue (one job per member and window, retried on failure, marked mailed once sent). Without Redis (development only) none is sent.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `Attachment`     | A file on an issue or a comment (`ownerType` `issue` or `comment`; `issueId` is the issue in both cases), in the organisation's database. Pictures (JPEG, PNG, WebP) and PDFs only, 10 MB each, 20 per owner; the bytes sit in a private S3 bucket (`organisations/<id>/attachments/<key>`) and are served only through the API, to members holding `attachment:read`, only while a record carries the key. A picture gets a 256 px WebP square thumbnail; a PDF gets a 256 px WebP preview of its first page (none when the PDF is damaged or encrypted). Deleting an issue or a comment deletes its files and their objects.                                                                                                                                                      |
| `Widget key`     | A project's public key (`pk_live_` and 32 characters), in the CORE database (`widgetKeys`, with its organisation and project) so the public endpoint finds the organisation before it opens a database. It reads its own configuration and files reports for its project, nothing else. It carries an allow-list of origins (at least one, `https://host[:port]`, `http://` for a local host only, no wildcard, no path), an `active` switch (off: the widget answers `enabled: false`), `revokedAt` (revoked: unknown to the endpoint) and `lastUsedAt` (to the minute). Created and rotated only with a recent proof of identity (`intake:manage`: admin, owner).                                                                                                                 |
| `Client report`  | What a reader sent through the widget, in the organisation's database (`clientReports`): title, description, optional e-mail, page URL, user agent, locale, flat metadata. States `new` -> `accepted` (an issue was made from it, in the project's Triage status; the issue carries `clientReportId`) or `declined` (with the team's reason) -> `closed` (its issue is done, cancelled or deleted; moving the issue back reopens it). Text from a stranger: shown as plain text only. Accepted and declined by those who write issues (`issue:write`); a new one is announced on `clientReportReceived`.                                                                                                                                                                            |
| `Tracking token` | `<organisation id>.<256 random bits, base64url>`, mailed once to a reporter who gave an e-mail, and kept only as a SHA-256. The UI's `/track/<token>` page reads it through `clientReportStatus` (UI server only: refused when the request has an `Origin`): the state, the title and the replies marked `public` (mention markers reduced to the label), never an author, an id, a private comment or the team's decline reason.                                                                                                                                                                                                                                                                                                                                                   |
| `Retention`      | A report settled 90 days ago (declined: from the decision; closed: from the closing) loses its e-mail, user agent and tracking token (`erasedAt`); its text stays. The `intake-retention` queue runs it every night at 03:30 UTC over every organisation.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `search`         | `search(query, kinds, first)` over issues (title, key, description), projects (key, name, description) and members (name, e-mail): one list per kind, best match first, at most `first` (1 to 50, default 10). Issues and projects use MongoDB text indexes (`issues_text`, `projects_text`; weights 10 on title, key and name, 1 on the description; no stemming, `default_language: none`), then a case-insensitive substring match fills the page (prefixes); an exact issue key (`ABC-12`) comes first. Members are matched in memory over the janus list (accent-insensitive; name, then e-mail). Each kind needs the permission of its module (`issue:read`, `project:read`, `member:read`): kinds default to those the viewer holds, and naming one the viewer lacks is 403. |

## Roles and permissions

One role per member per organisation (`src/core/access/roles.ts`); the grants are each module's
`defaultGrants`. The owner holds every declared permission. `organisation:create` is not a role's
permission: every signed-in account holds it (`src/core/access/account.ts`).

| Permission                                            | owner | admin | member | viewer |
| ----------------------------------------------------- | :---: | :---: | :----: | :----: |
| `organisation:read`                                   |  yes  |  yes  |  yes   |  yes   |
| `organisation:manage`                                 |  yes  |  yes  |   -    |   -    |
| `member:read`                                         |  yes  |  yes  |  yes   |  yes   |
| `member:manage` (invitations, role changes, removals) |  yes  |  yes  |   -    |   -    |
| `member:assign_owner`                                 |  yes  |   -   |   -    |   -    |
| `project:read`                                        |  yes  |  yes  |  yes   |  yes   |
| `project:manage`                                      |  yes  |  yes  |   -    |   -    |
| `issue:read`                                          |  yes  |  yes  |  yes   |  yes   |
| `issue:write`                                         |  yes  |  yes  |  yes   |   -    |
| `issue:delete`                                        |  yes  |  yes  |   -    |   -    |
| `comment:read`                                        |  yes  |  yes  |  yes   |  yes   |
| `comment:write`                                       |  yes  |  yes  |  yes   |   -    |
| `comment:delete`                                      |  yes  |  yes  |   -    |   -    |
| `attachment:read`                                     |  yes  |  yes  |  yes   |  yes   |
| `attachment:write`                                    |  yes  |  yes  |  yes   |   -    |
| `attachment:delete`                                   |  yes  |  yes  |   -    |   -    |
| `intake:manage` (widget keys, reports)                |  yes  |  yes  |   -    |   -    |

Inviting, changing a role, removing a member and enrolling a second factor also ask for a recent
proof of identity (10 minutes; 403 `auth.errors.step-up-required`, then `requestStepUp` /
`confirmStepUp`).

## Mail links

The UI pages the mails link to, fixed here (the UI never renames them alone). Each posts its token
back from a button: a mail scanner follows a link, so a GET never spends it.

| Path                          | Mail           | Mutation                   |
| ----------------------------- | -------------- | -------------------------- |
| `/invitations/accept?token=`  | invitation     | `acceptInvitation`         |
| `/auth/magic-link?token=`     | sign-in link   | `confirmMagicLink`         |
| `/auth/reset-password?token=` | password reset | `resetPassword`            |
| `/auth/verify-email?token=`   | e-mail proof   | `confirmEmailVerification` |

The sign-in link is behind `PULSARIX_MAGIC_LINK` (off by default; `.env.example`, `deploy/.env.example`). Off, `requestMagicLink` answers true and sends nothing, `confirmMagicLink` is refused 503 `auth.errors.unavailable`, and `authConfig { magicLink }` is false so the sign-in screen hides the option.

**E-mail verification.** `signUp` does not prove the e-mail (`Viewer.emailVerified` is false). The signed-in account calls `requestEmailVerification`, which answers true whether or not the e-mail is proved already (then nothing is sent): the mail runs in the background, and the 429 comes from the account's Redis limit (10 an hour, `accounts.email-verification-account`, 503 if Redis cannot be asked) and janus's per-address throttle (5 per 10 minutes). `/auth/verify-email` posts its token to `confirmEmailVerification`, which needs a session and is bound to it: a token issued to another account is `auth.errors.invalid-token` and stays usable by its owner. The link proves the address only; the password and the second factor are kept (a first proof through a sign-in link or an invitation still drops them). It adds no error code: a lapsed, spent, unknown or foreign token is `auth.errors.invalid-token`.

## File routes

Files do not go through GraphQL. The routes sit beside `/graphql` and need the same headers
(`x-pulsarix-client`, `Authorization: Bearer`, `x-organization-id`); without `S3_BUCKET`,
`S3_ACCESS_KEY` and `S3_SECRET_KEY` they answer 503 `attachments.errors.unavailable`.

| Route                                                                                                             | Needs                                                                           | Answers                                                                                                                                                                                                                                                                         |
| ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PUT /media/attachments?ownerType=issue\|comment&ownerId=&fileName=` (raw body, `Content-Type`, `Content-Length`) | `attachment:write`; for a comment, being its author or holding `comment:delete` | `{ id, key, size, previewKey }` once the file, its thumbnail and its record are stored; 415 type (or bytes that are not that type), 413 size, 422 unreadable or smaller than 16 px, 409 the owner has 20 files, 404 no such owner, 400 bad `ownerType`, `ownerId` or `fileName` |
| `GET /media/attachments/<key>` and `/<key>/256`                                                                   | `attachment:read`                                                               | the file (or the thumbnail), with Range, ETag and `Content-Security-Policy: sandbox`; 404 for a key no record of the organisation carries                                                                                                                                       |

`attachments(ownerType, ownerId)` lists the files with their `url` and `previewUrl`;
`issueAttachments(issueId)` lists the files of an issue and of all its comments in one query;
`deleteAttachment(id)` removes one (its uploader, or `attachment:delete`). An upload and a delete are
journalled in the issue's activity as an `updated` row with one change, field `attachment` (`to` the
file name for an upload, `from` it for a delete), so the issue's watchers are notified like any
other change.

## Public endpoint

`POST /public/graphql` is the product's only unauthenticated surface, apart from `/graphql`'s own
sign-in mutations. It has a schema of its own (three fields) and runs three **persisted operations**,
named by `id` (`{ "id": "widgetConfig", "variables": {...} }`); a document, an introspection query or
any other key is 400 `intake.errors.persisted-only`. The body is JSON only (415 otherwise) and at most
64 KiB.

| `id`                 | Variables                                                                                                                                                                | Answers                                            | Needs                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------- | ----------------------------------------------- |
| `widgetConfig`       | `publicKey`                                                                                                                                                              | `projectName` (null when off), `locale`, `enabled` | the key; an `Origin` in its allow-list          |
| `submitClientReport` | `publicKey`, `input` (`title` 200, `description` 10 000, `email?`, `pageUrl?`, `locale?`, `metadata?` 20 entries / 2 KB, `website` honeypot, `filledInMs` at least 3000) | `reportId`, `tracking`                             | the key; an allowed `Origin`; the limits below  |
| `clientReportStatus` | `token`                                                                                                                                                                  | `state`, `title`, `createdAt`, `replies`           | the UI server: no `Origin`, `x-pulsarix-client` |
- **CORS** answers only an origin some live key allows (the preflight), and every call checks the key's
  own list; a foreign or missing `Origin` is 403 `intake.errors.origin-not-allowed` with no CORS header.
  A browser sends `Origin`; a script can forge it, so it is a guard against other sites, and the limits
  are the guard against scripts.
- **Rate limits** (`@softistx/redis`, `src/modules/intake/intake.limits.ts`): per address 120 reads or
  submits per 10 minutes; per key 60 per hour; per address and key 5 per 10 minutes; per e-mail 3 per
  hour; per organisation 300 per hour; tracking reads 30 per 10 minutes per address. Over a limit: 429
  `intake.errors.too-many-requests` with `Retry-After`. Without Redis (or if it fails) the endpoint
  answers 503 `intake.errors.unavailable`: it never runs unmetered. The address is `TRUSTED_PROXIES`'
  reading of `X-Forwarded-For`; unset, it is the connection's; an IPv6 address counts by its /64. The UI server's tracking reads share one bucket per client only if it appends the client's address to `X-Forwarded-For` from inside `TRUSTED_PROXIES`.
- **Anti-abuse** (Q10): the honeypot field `website` (told it worked, nothing kept), a minimum fill time
  (`filledInMs`, 400 `intake.errors.too-fast`), the length limits, control characters stripped, and the
  tracking mail repeats nothing the sender typed.
- Every answer carries `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex`.
